# D202 bitstream·요구사항 리뷰 — 2026-10-28

검토 대상은 hs_dmd `9cfd1f4`, dlpc410 `3302b8c`, DMD-FPGA-Test `cd5666f`입니다. JTAG 파일 SHA-256은 `f88f5a2c105ba33f6bb58b18e802095f4ccd340795d7a084d066c3a0981ce268`입니다. 기존 Test 작업 폴더의 미커밋 애니메이션 변경은 이 릴리스 판정 범위에 넣지 않았습니다.

**판정: 기본 기능은 구현됐지만, 오류 없음·요구사항 전체 충족으로 승인할 단계는 아닙니다. 추가 ISim 검사에서 아래 네 경계 문제가 재현됐습니다.** RTL/기존 bitstream은 수정하지 않았고, 장치 접근·재합성·업로드는 하지 않았습니다.

**리뷰 이후 사용자 확인(2026-10-28):** “최신 bitstream에는 pattern 잘 upload됨. number patterns 잘 보여.” 최신 bitstream의 기본 업로드·숫자 패턴 표시 성공을 사용자 실기 확인으로 반영합니다. 아래 네 항목은 오류·중단·동시 제어·통계 갱신 경계에서 재현된 문제이므로 정상 업로드·표시 성공과 함께 기록합니다. 이 메시지에는 파일 SHA-256이나 ABI 읽기 결과가 포함되지 않아 특정 산출물 해시와의 대응은 확정하지 않습니다.

## 확인된 문제

### R1 — P1: 재생 중 오류에도 MCP와 정상 완료 펄스를 출력

[memory_playback.v](../../APPSFPGA_MEM/src/rtl/memory_playback.v)의 112행은 streamer의 commit 허용을 `countdown == 0`만으로 결정합니다. 275–291행은 오류가 있어도 진행 중 frame_done을 기다리며, 정상 완료 분기가 설정한 done_q를 오류 분기가 취소하지 않습니다. 334행은 done_q만 보고 sync_done을 만듭니다.

재현: 한 프레임을 읽는 중 첫 ROW_GAP에서 memory_error를 1로 유지하고 나머지 FIFO 응답을 계속 공급했습니다. 그 뒤 MCP가 발생했고 최종 상태는 **reason=3(error), done=1, sync_done=1**이었습니다. sync 출력도 활성화한 조건입니다. 광학 출력을 실측한 결과가 아니라, 오류 입력 이후에도 실제 RTL이 MCP/완료 명령을 생성한 결과입니다.

영향: 메모리 오류가 난 프레임을 표시할 수 있고, 후속 계측기는 정상 완료 펄스로 오인할 수 있습니다. 기존 회귀 harness는 memory_error가 나오면 즉시 테스트를 끝내므로 오류 이후의 동작을 검사하지 못했습니다.

수정 방향: 오류를 해당 프레임에 latch하고 MCP/정상 done/sync_done을 억제합니다. 이미 요청한 DDR 응답은 안전하게 drain한 뒤 오류 종료하도록 구분해야 합니다. commit만 막으면 WAIT_COMMIT에 갇힐 수 있으므로 별도의 오류 종료 경로가 필요합니다. MCP 이후 발생한 오류는 이미 출력된 화면을 되돌릴 수 없으므로 그 시점을 구분해 기록해야 합니다.

### R2 — P2: 끊긴 시퀀스 설정이 실행 가능한 상태로 남음

[memory_playback.v](../../APPSFPGA_MEM/src/rtl/memory_playback.v)의 126–146행은 활성 테이블에 직접 씁니다. 174–176행은 개별 설정 쓰기마다 configured_generation을 현재 generation으로 갱신하며, 225행에는 설정 전체가 완료됐는지 확인하는 조건이 없습니다.

재현: 정상 설정 `[0,1]`을 `[1,0]`으로 바꾸다가 첫 엔트리만 쓴 뒤 중단했습니다. 마지막 `0x2A=5`도 보내지 않았습니다. 이후 실제 Start 경로와 같은 `0x2A=0x0D`를 보내면 **running=1**, DDR 읽기 순서 **[1,1]**을 관찰했습니다. 슬롯은 모두 valid이므로 preflight가 통과합니다.

실제 API도 [dmd_memory.ps1](../../../dlpc410/dmd_ctrl/memory/dmd_memory.ps1) 265–275행에서 길이/반복/테이블을 순차적으로 쓰고, Write-Reg 실패 시 예외로 중단합니다. 전송 중단 후 재설정을 끝내지 않고 Start를 요청하면 이런 부분 설정을 실행할 수 있습니다. 이 리뷰는 USB 장애 자체를 발생시킨 것이 아니라, 설정 전송이 중단된 동일한 레지스터 상태를 재현했습니다.

수정 방향: 설정 시작/첫 변경에서 config_valid를 해제하고, 검증된 전체 설정을 명시적으로 commit한 뒤에만 START/TTL을 허용합니다. 기존 설정을 보존해야 한다면 staging table 또는 이중 테이블이 필요합니다. 단순한 generation 일치 검사는 설정 완결성을 보장하지 않습니다.

### R3 — P2: TTL arm 상태에서 RTL 설정 변경이 허용됨

[memory_playback.v](../../APPSFPGA_MEM/src/rtl/memory_playback.v) 126–127행의 테이블 쓰기와 203행의 설정 쓰기 허용 조건에 `!armed`가 없습니다.

재현: `0x2A=0x15`로 arm한 뒤 `0x38=7`을 쓰면 **armed=1을 유지한 채 repeat_count가 7로 변경**됩니다. 명세의 정지·disarm 후 설정 원칙을 RTL이 강제하지 않습니다.

일반적인 단일 API 호출에서는 `Require-Stopped`가 이 요청을 막습니다. 다만 management PS의 mutex와 달리 [dmd_playback.ps1](../../../dlpc410/dmd_ctrl/memory/dmd_playback.ps1)의 Start/Arm/Stop은 같은 mutex를 사용하지 않으므로, 병렬 제어에서 최초 확인 뒤 ARM이 들어오거나 raw register를 쓰는 경우 FPGA에서 보호되지 않습니다. 병렬 프로세스 경쟁 자체는 이번 시뮬레이션에서 실행하지 않았으며, RTL 허용 동작과 두 PS의 잠금 차이를 각각 확인했습니다.

수정 방향: RTL에서 arm 중 설정/테이블 쓰기를 거부하고, 모든 제어 동작이 공유하는 host 잠금 및 설정 commit 경계를 마련합니다.

### R4 — P2: snapshot의 마지막/최소/최대 간격이 서로 다른 갱신 단계를 담음

[memory_playback.v](../../APPSFPGA_MEM/src/rtl/memory_playback.v) 324–331행에서 interval_q는 MCP 때 갱신하지만 min/max는 한 클럭 뒤 갱신합니다. 336–340행은 이 갱신 중간에도 snapshot을 수락합니다.

재현: 두 번째 MCP 직후 해당 경계에 snapshot을 요청하면 **frames=2, last=10976 ticks, min=0, max=0**이 나옵니다. 몇 클럭 뒤에는 **last=min=max=10976**이 됩니다. 10976은 이 단순 FIFO fixture에서 발생한 간격이며 기존 MIG 모델의 성능 수치와 비교하지 않습니다.

영향: 재생 중 통계를 수집할 때 실제 표본이 있는데 최소/최대가 0이거나 이전 표본 기준일 수 있습니다. 완료 후 충분히 기다려서 읽는 기존 테스트에서는 드러나지 않았습니다.

수정 방향: interval pipeline이 끝난 시점에 snapshot을 확정하거나, 동일한 사건 기준의 next-state 값을 한 번에 저장하고 완료 응답을 제공합니다.

## 빌드 및 검증 근거

- 릴리스 manifest의 **93개 파일 해시**, 현재 **80개 빌드 입력 해시**가 모두 일치합니다. 이번 검토에서 기존 bitstream 바이너리는 바꾸지 않았습니다.
- 기존 ISE 보고서: 합성 오류 0, PAR/TRCE 타이밍 오류 0/Score 0, BitGen DRC 오류 0. setup 여유는 200MHz +0.025ns, 150MHz +0.038ns입니다. 합성 경고 2151, DRC 경고 25가 남아 있습니다.
- 타이밍 통과는 현재 UCF 검사 범위에 한정됩니다. 기존 USB OFFSET IN에 VALID duration이 없어서 일부 입력 hold 검사가 빠지고, vendor TIG 경고가 남습니다.
- 기존 릴리스 검사 기록은 API 27개, Test 12개, JTAG 도구 18개, RTL 3종 통과입니다. 이 숫자는 10월 27일 기록이며 이번에 전부 재실행했다는 뜻이 아닙니다. 이번에는 변경되지 않은 실제 RTL에 추가 경계 probe를 실행했습니다.
- 추가 probe는 valid 디렉터리 두 슬롯을 초기화하고 한 클럭 FIFO 응답·항상 ready인 메모리를 사용합니다. 실제 CRC/DDR2/USB/DMD를 테스트하는 fixture가 아니며, 네 FSM/통계 경계 조건만 재현합니다.
